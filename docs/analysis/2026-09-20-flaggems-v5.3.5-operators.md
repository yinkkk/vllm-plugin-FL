## 1. 先看最值得关注的算子

**第一组：FL 已有显式接入，优先确认实际命中。**

- `rms_norm`、`fused_add_rms_norm`：归一化和残差融合。
- `silu_and_mul`：SwiGLU 中 SiLU 与乘法融合。
- `apply_rotary_pos_emb`：Q/K 的 RoPE，支持原地路径。

**第二组：通过普通 PyTorch/ATen 或特定后端进入，需要 trace。**

- `mm`、`mm_out`、`addmm`：线性投影、FFN、LM head 的 GEMM 候选。
- `embedding`、`argmax`、`softmax`、`log_softmax`、`topk`、排序和张量搬运：embedding、采样或辅助计算候选。

**第三组：库里有，当前默认 attention 路由却不一定用。**

- `flash_attn_varlen_func`：变长 GQA / 分页 KV attention。
- `reshape_and_cache_flash`：K/V 写入分页缓存。

天数默认通过 FL 选择 vLLM `TRITON_ATTN`，沐曦默认选择 MACA attention；不能因安装了 FlagGems 就把上述 attention 算子认定为默认热点。

## 2. 算子库的架构特性

```text
模型层显式调用 / PyTorch ATen 调用
              ↓
FlagGems 公共函数与模块接口
              ↓
通用实现 → 厂商覆盖 → 架构特化 → Triton 版本特化
              ↓
Python/Triton 路径，或满足条件的 C 扩展路径
              ↓
启发式 / autotune / 缓存后的 kernel launch
```

### 2.1 两类接入接口

`flag_gems.enable()`、`only_enable()` 和 `use_gems` 通过 `torch.library` 注册相应 ATen 实现；FL Worker 使用前两者启用全量、黑名单或白名单。另一类接口是直接调用融合函数，例如 `flag_gems.silu_and_mul(x, y)`，以及 `gems_rms_forward` 等模块包装。

因此，ATen 注册清单、库导出的融合函数、FL OOT 名称并不完全相同。`rms_norm` 的模块路径可在带 residual 时实际调用 `fused_add_rms_norm`。

### 2.2 厂商和架构覆盖

`SpecOpRegistrar.apply()` 依次应用 vendor、architecture、Triton version 事件，将同名函数覆盖到公共命名空间。实际函数可以不是 `src/flag_gems/ops/` 中看到的通用实现。

本 tag 的 `_metax/ops/__init__.py` 和 `_iluvatar/ops/__init__.py` 均明确导出 `mm` / `mm_out`。两种卡上的矩阵乘优化，应先看厂商文件，而不是默认修改通用 `ops/mm.py`。

### 2.3 C 扩展不是自动开启

`config.py` 默认 `use_c_extension=False`，需要 `USE_C_EXTENSION=1` 且可用的扩展加载成功才切换。Norm、RoPE、attention、KV 写入的模块/函数存在相应分支；不应假设改了 Python kernel 后 C 扩展也同步改变。

源码依据：[公共注册入口](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/__init__.py)、[SpecOpRegistrar](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/runtime/backend/__init__.py)、[扩展配置](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/config.py)。

## 3. 与 MiniCPM5-2B 计算图的对应关系

以已核对的官方配置、TP=1 为前提，T 表示本轮实际处理 token 数，不是固定请求数。以下是模型结构推导的典型形状，不是实测 trace。

| 模型步骤 | 典型形状/运算 | FlagGems 候选 | 接入判断 |
|---|---|---|---|
| Token embedding | token IDs → `[T,2048]` | `embedding` / 索引类 | 条件性，vLLM 可能走其他 gather/custom op |
| Attention 前 Norm | `[T,2048]` | `rms_norm` / `fused_add_rms_norm` | 已有 FL 模块适配 |
| QKV 投影 | `[T,2048] × [2048,2560]`，若合并 | `mm` / `addmm` | ATen 或 linear 实现决定 |
| RoPE | Q=`[T,16,128]`、K=`[T,2,128]` | `apply_rotary_pos_emb` | 已有 FL 模块适配 |
| KV 写入 | 每 token 两组 `[2,128]` K/V | `reshape_and_cache_flash` | AttentionFL 路径明确调用 |
| GQA | 16 个 Q heads 共享 2 个 KV heads | `flash_attn_varlen_func` | 可选 AttentionFL 路径 |
| Attention 输出投影 | `[T,2048] × [2048,2048]` | `mm` | 需 trace |
| FFN 前 Norm | `[T,2048]` | 同上 | 已有 FL 模块适配 |
| gate/up 投影 | `[T,2048] × [2048,12288]`，若合并 | `mm` | 需 trace |
| SwiGLU | 两个 `[T,6144]` 输入 → `[T,6144]` | `silu_and_mul` | 已有 FL 模块适配 |
| down 投影 | `[T,6144] × [6144,2048]` | `mm` | 需 trace |
| Final Norm / LM head | 2048 → 130560 词表 | `rms_norm`、`mm` | LM head 可能只算需要采样的位置 |
| 采样 | logits → token | `argmax` / `topk` / `softmax` 等 | 取决于采样配置和 sampler 实现 |

模型配置依据：[官方 config.json](https://huggingface.co/openbmb/MiniCPM5-2B/blob/main/config.json)。模型源链接会变化，实验时保存实际 config 和权重 revision。

## 4. RMSNorm 与残差融合

### 4.1 RMSNorm 的算法

对每行 x：`y = weight × x / sqrt(mean(x²) + eps)`。通用实现对 FP16/BF16 使用 FP32 计算平方和与逆 RMS；代码在乘 weight 前把归一化结果转换回输入 dtype，以贴近 vLLM native 的数值顺序。

该 tag 的 `rms_norm_forward()`：

- `N <= 4096`：每行一个 Triton program，BLOCK_SIZE 为 N 的上取整 2 次幂。
- `N > 4096`：循环归约，再逆序读取并归一化，尝试利用 L2；循环 kernel 使用已有调参配置。
- 创建输出和每行 FP32 `inv_rms`，支持反向接口。

对 MiniCPM 的 `N=2048`，预计命中小行宽路径，**不会因为 FFN intermediate=6144 就自动进入 Norm 大行宽路径**，Norm 的归一化维度仍是 hidden size。

### 4.2 fused_add_rms_norm 的算法

先求 `z=x+residual`，再归一化 z；同时更新 residual 与 x。小行宽路径将加法和归一化放进一个 kernel，减少一次独立加法和中间结果往返。

接口文档说明原地更新，但 Python 包装会对 x/residual/weight 调用 `.contiguous()`；非连续输入可能产生副本，所以正确性测试要同时检查返回对象与调用者对 alias 的预期。

`N<=4096` 为单行路径，`N>4096` 为两遍循环。BF16 下融合与非融合的舍入位置不同，不应随意把两条路径的转换步骤统一成“更高精度版本”。

### 4.3 优化空间

先测 small T 的启动开销、row-wise 并行度、连续化和临时分配；若热点明显，考虑一 program 多行或复用缓冲。这里已有 residual 融合，不需要从头写“首次融合”。

源码：[rms_norm.py](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/ops/rms_norm.py)、[fused_add_rms_norm.py](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/fused/fused_add_rms_norm.py)、[模块包装](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/modules/normalization.py)。

## 5. SiLU+Mul：现成的 SwiGLU 融合

算法为 `out = (x / (1 + exp(-x))) × gate`。`silu_and_mul.py` 的 scalar body 把 x 转为 FP32 计算 sigmoid/SiLU，再相乘；`pointwise_dynamic` 生成张量级逐元素 kernel。

FL 把合并 gate/up 输出分为两个 view，传给 `gems_silu_and_mul`。库里同时有 `silu_and_mul_out`，但当前 FL 模块包装调用的是普通返回新输出的版本。若想复用输出缓冲，必须改接入并确认 graph、生命周期和别名安全，不能仅更改底层函数名。

可测机会：6144 列、实际 T、split 后的 stride、launch 数和输出分配。这里已经将 SiLU 与乘法融合；真正进一步融合 GEMM epilogue 或 down projection 是更大工程，需要先证明收益。

源码：[silu_and_mul.py](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/fused/silu_and_mul.py)、[activation 模块](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/modules/activation.py)。

## 6. RoPE 与分页 KV 写入

### 6.1 RoPE

对向量成对维度施加旋转：`x1'=x1*cos-x2*sin`、`x2'=x2*cos+x1*sin`。实现支持 interleaved / 非 interleaved、Q/K 不同 head 数、position_ids、原地和非原地输出。

通用 `apply_rotary_pos_emb` 检查 cos/sin 宽度为 head_dim 的一半，并把输入 reshape 为 token/head/dim。当前原地 kernel 以 token 为 grid，处理该 token 的 Q/K；FL 默认传入 inplace=True。模型完整 head_dim=128 是有代表性的调优形状。

注意：FL 对部分 rotary_dim 会拆分 passthrough 再 cat；不要把这种其他模型路径的开销自动归到 MiniCPM 的完整 RoPE 路径。

### 6.2 reshape_and_cache_flash

该 kernel 以 token 为并行单位，从 `slot_mapping` 计算：

```text
block_idx = slot_idx // block_size
block_offset = slot_idx % block_size
```

再把该 token 的 K/V 写入分页 cache；负 slot 被跳过。通用 Python/Triton 路径目前直接存值，源码留有 FP8 支持待实现标记；签名带 scale 不代表已经完成量化 cache 算法。

对 MiniCPM，每 token 的 K 或 V 宽度是 `2×128=256` 元素。融合 RoPE 和 cache 写入可能减少 launch/中间访问，但当前并没有一个可直接替换完整 MiniCPM 路径的通用融合接口；需处理 Q 输出、K 旋转、V 写入及 vLLM 原有 cache 更新时序。

源码：[rotary_embedding.py](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/fused/rotary_embedding.py)、[reshape_and_cache_flash.py](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/fused/reshape_and_cache_flash.py)。

## 7. GEMM：两个厂商已经有不同算法路径

### 7.1 共性

GEMM 计算 `C[M,N]=A[M,K]×B[K,N]`。Triton 实现将 M/N 分块，沿 K 循环，调用 `tl.dot` 并使用 FP32 accumulator；block 大小、warps、stages 和访问布局影响寄存器、片上存储和硬件利用率。

split-K 把同一输出块的 K 归约拆给多个 program，增加并行度，代价是额外归约、缓冲或 atomic。它可能适合输出 tile 数不足的形状，但不意味着所有 decode GEMM 都应该开启。

### 7.2 天数 `_iluvatar/ops/mm.py`

- `libtuner` 使用 M/N/K 为调参 key，结合 `early_config_prune` 和 `estimate_matmul_time`，保留 top 15 候选。
- grid 包含输出 tiles 和 `SPLIT_K` 维度。
- `GROUP_M=8` 做 tile 调度分组，改善数据复用机会。
- `SPLIT_K=1` 直接 store，否则 atomic add；候选启用时必须核对输出清零/初始化与累加数值语义，不能只改 YAML 就忽略此约束。
- 对两维都不连续的输入执行 contiguous；`mm_out` 可使用预分配输出。

它依赖 `triton.ops.matmul_perf_model`，比赛 FL 分支也有针对旧天数 Triton 的时钟/编译兼容补丁。因此“换新版通用 Triton”不是安全的调优替代方案。

### 7.3 沐曦 `_metax/ops/mm.py`

该 tag 已包含按形状/布局选择的多路线 dispatcher，顺序大致如下：

| 触发条件 | 路线 | 意义 |
|---|---|---|
| `N==1` | GEMV，部分情形沿 K 并行 | 专门处理单列输出；注意不是 `M==1` |
| 两步 split-K 条件成立 | partial workspace + reduce | 当前条件包含 `N==256`、`K>=2048` 和 SM/L2 预算 |
| 普通 split-K 条件成立 | 清零输出后 split-K | 依据输出并行度和 L2 atomic working set |
| 连续 NN 布局 | `mm_kernel_nn` | 去除一般 stride 处理的布局特化 |
| 连续 NT 布局 | `mm_kernel_nt` | 常见权重转置布局特化 |
| 其他合法布局 | 通用 kernel | 兜底 |

**一个容易踩的形状陷阱：** 单 token linear 通常是 `M=1`，不是 `N=1`，因此不自动进入上表 GEMV 分支。MiniCPM 的单独 K/V 投影宽度可以是 256，但若 vLLM 合并 QKV，N 会是 2560，也不满足 N=256 的两步 split-K 条件。必须用真实 trace 验证。

### 7.4 通用 mm 不是两卡的默认调优目标

通用 `ops/mm.py` 还包含 SYRK 特判、Stream-K 和 cluster-remote 候选。Stream-K 条件有设备 capability 和连续布局限制，代码注释提到 A100 验证；两卡又有 vendor override。不能因通用目录有这些算法，就宣称 C500/BI-V150 正在执行。

源码：[天数 mm](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/runtime/backend/_iluvatar/ops/mm.py)、[沐曦 mm](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/runtime/backend/_metax/ops/mm.py)、[通用 mm](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/ops/mm.py)。

## 8. Attention：算法存在与接口可用性要分开

`ops/attention.py::flash_attn_varlen_func` 支持变长序列、MQA/GQA、因果 mask、滑动窗口、ALiBi、softcap、分页 block table 和可选 log-sum-exp 输出。

底层 `flash_kernel.py` 的关键算法是分块 QK、在线 softmax 和 PV 累加：遍历 K/V 块，维护每行最大值、指数和及输出累加器；当最大值变化时缩放旧累加结果，最终归一化。它避免将整个 Q×K 分数矩阵写入显存。GQA 通过 head 映射共享 K/V，不要求物理复制成与 Q 相同 head 数。

接口边界已经在代码里明确：

- `fa_version != 2` 报错。
- `num_splits > 0` 报错。
- `cu_seqlens_k` 与 `seqused_k` 必须提供其一且不能同时提供。
- 分页模式要求 `seqused_k`。
- 底层标准前向检查 FP16/BF16、最后一维连续、head_dim≤256 且满足对齐、Q heads 可被 KV heads 整除等。

底层库确实还有 split-KV kernel 和非 varlen 调度路径，但这不代表 FL 使用的 varlen 接口允许外部设置 num_splits。调 split-KV 前先确认入口、实现和缓存布局，不能仅打开一个未经支持的参数。

**对比赛的适用性：** MiniCPM 的 BF16、head_dim=128、16:2 GQA 在数学/形状上属于该接口目标范围；两卡的编译与数值仍待实测。天数需显式选入 AttentionFL 才能直接评估该路径，沐曦还需改变 vendor 默认选择；这些后端替换须符合比赛规则。

源码：[attention API](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/ops/attention.py)、[flash_api.py](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/ops/flash_api.py)、[flash_kernel.py](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/ops/flash_kernel.py)。

## 9. 采样、embedding 与辅助算子

| 算子类 | 可以用于哪里 | 不能直接推出的结论 |
|---|---|---|
| `embedding` | token ID 查表 | vLLM 一定调用标准 ATen embedding |
| `argmax` | greedy token 选择 | 官方随机采样可改成 greedy |
| `softmax`、`log_softmax` | 概率与 logprob | FlashAttention 内部一定调用独立 softmax |
| `topk`、sort、cumsum、mask | top-k/top-p 过滤及辅助处理 | 单独 topk 可以替代完整 top-p sampler |
| `mm`/`addmm` | 输出词表投影 | 可以只算部分词表而不影响输出分布 |
| copy/contiguous/index/reduction | 输入准备、布局转换和状态维护 | 每个小算子都有值得单独优化的占比 |

沐曦 FL 补丁将上游 top-k/top-p 过滤转到 PyTorch fallback，这使这些基础算子值得观察。但必须沿实际 sampler 检查：PyTorch fallback 不等于 CPU fallback，也不保证每一步都被 FlagGems 接管。

`fused/topk_softmax.py`、`grouped_topk.py` 主要服务 MoE gating，不能因为名称里有 topk/softmax 就用来替换语言模型采样。

## 10. 调优基础设施：已有能力怎么用

### 10.1 libentry / libtuner / pointwise_dynamic

- `libentry`：kernel 入口包装与 dispatch 缓存，降低重复 Python/JIT 路径的开销。
- `LibTuner` / `libtuner`：构建候选、prune、benchmark 并缓存配置；key 和候选集合依赖具体 kernel。
- `pointwise_dynamic`：为逐元素表达式生成处理张量布局与类型提升的实现，SiLU+Mul 已使用。
- vendor 的 `tune_configs.yaml`：已有硬件候选配置，先确认目标 kernel 消费哪个配置名，再修改。

### 10.2 FlagTune 三种模式

`runtime/flagtune.py::resolve_tuning_mode()` 区分 Default、Expanded、Cost Model：

| 设置/条件 | 模式含义 |
|---|---|
| `USE_FLAGTUNE=0` | 默认候选空间；不是关闭所有 Triton autotune |
| `USE_FLAGTUNE=1` 或选入 `FLAGTUNE_INCLUDE`，但无可用 cost model | 扩展搜索 |
| 算子支持 cost model 且平台模型包可用 | 可走 cost model；默认行为还受显式环境变量影响 |
| 支持 cost model 但显式 `USE_FLAGTUNE_COST_MODEL=0` | 扩展搜索 |

不能推断 BI-V150/C500 已经附带可用 cost model，也不能推断每个算子都接入 FlagTune。正式测试需记录模式与缓存，区分首次调优成本和稳态推理；扩展搜索应在独立预热/开发阶段进行。

源码：[libentry / LibTuner](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/utils/libentry.py)、[FlagTune 模式选择](https://github.com/flagos-ai/FlagGems/blob/a7620cc191a0b42e040194622c5758b22a7a25dc/src/flag_gems/runtime/flagtune.py)。

## 12. 建议的阅读与优化顺序

1. **确认实际路径。** 同时记录 FL attention 类路径、FlagGems 函数来源、C 扩展开关、白名单和 profiler 结果。
2. **先看厂商 GEMM。** 覆盖真实 QKV、FFN、LM head 形状；检查是否命中特化，避免优化没有被调用的通用 mm。
3. **看已接入的 Norm 与 SiLU。** 易于隔离验证，重点是现有融合的执行效率，不重复实现融合本身。
4. **再决定 attention 投入。** 天数默认应先分析 vLLM Triton；沐曦默认应先分析 MACA。选择 FlagGems attention 是独立对照实验。
5. **RoPE/KV 融合和采样专项留给证据。** 有明确端到端占比再做，防止单算子收益淹没在总时长中。

库中还包含 MLA、DSA、稀疏 attention、MoE、FP8/INT8/INT4 与训练反向算子。这说明库的覆盖面广，不说明 MiniCPM5-2B 应使用这些算法。当前目标是标准 BF16 稠密 GQA 推理，优先围绕本报告列出的实际计算图收敛。

最终应形成“源码入口 → 实际命中 → 算子正确性 → 微基准 → 端到端吞吐与精度”闭环；仅存在一个 API 或跑出一次更快的 kernel 时间，都不足以认定比赛优化成立。
